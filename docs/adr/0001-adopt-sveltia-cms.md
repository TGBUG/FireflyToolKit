# Adopt Sveltia CMS instead of building a custom writing frontend

FireflyToolKit's goal is comfortable blogging, not owning a CMS. Sveltia CMS covers the entire writing surface — file tree, Markdown editor, media library, frontmatter forms — as two static files (`public/admin/index.html` and `public/admin/config.yml`) with no server. Authentication is a fine-grained PAT held in the operator's browser, which is viable only because each blog is single-user: GitHub requires a client secret during token exchange for every other flow, so any multi-user or hosted-auth shape would have forced an OAuth proxy.

The accepted cost: the password gate is gone. Sveltia's admin page is a public static page, and the only thing between an attacker and the repository is possession of the PAT. A future reader comparing this against the original design's session-cookie auth should know that was a deliberate trade, not an omission.

Considered and rejected: **Decap CMS** and **Pages CMS**. Pages CMS is a hosted GitHub App with less setup, but its documented weaknesses land exactly on Firefly's conventions — forced `+00:00` timezones against a `z.date()` field, and poor handling of content and images sharing a directory.

Decap was reconsidered later, when multi-branch drafts became a requirement, because it is the CMS whose Editorial Workflow is long established. Sveltia shipped the same capability in the meantime (see ADR-0008), so the question became whether Decap's version justified its authentication cost. It does not. Decap's GitHub backend cannot authenticate without an OAuth client server, which means an always-on service, a client secret to rotate, and — because `*.workers.dev` is blocked from mainland China — that service running on the blog's own VPS, making CMS login depend on VPS uptime and routing the login redirect through `github.com`. The access-token path Decap users resort to is explicitly unsupported. Sveltia offers the same draft workflow while keeping the PAT, so no server is needed at all. Decap also has not supported mobile since 2017.

The bundle is self-hosted rather than loaded from a CDN. `sveltia-cms.js` is 2.1 MB and measured at roughly 22 seconds from mainland China on both unpkg and jsDelivr, which leaves the admin interface unstyled and inert — a failure that looks like a broken product but is purely a delivery problem. Serving it from the blog's own origin removes the dependency and the latency. It is committed into FireflyToolKit's package rather than fetched during `inject`, so injection is reproducible and works offline; upgrades cost a few megabytes of history each.

Self-hosting covers the bundle and its lazy chunks, which resolve relative to the script's own URL. It does **not** cover the interface translations or the syntax highlighter. Sveltia fetches locale JSON from `https://unpkg.com/@sveltia/cms@<version>/locales/<locale>.json` behind a five-second `AbortSignal.timeout`, and pulls Shiki engines and grammars from unpkg on demand; only the built-in `en-US` strings ship inside the bundle. So the admin interface is English here, and code blocks in the editor's preview may go unhighlighted — the published site is unaffected, because the theme highlights at build time. A five-second stall followed by a silent fallback to English is an acceptable failure; rewriting the fetches to local files would fix the language and then rot on the next upgrade.
